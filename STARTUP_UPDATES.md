# Обновление при привычном запуске

Для менеджера: запустить привычный start.bat. Программа проверит стабильный
релиз, подготовит обновление и запустится. Папку выбирать и ключи переносить
не нужно. На Mac используется привычная команда/оболочка запуска; живой тест
остаётся запланированным на 26 октября 2026.

## Что реализовано

* start.py вызывает startup_update.py перед запуском отправителя. --no-updates
  пропускает проверку сети и использует уже выбранную активную установку.
* Проверяется только GitHub releases/latest, prerelease/draft игнорируются.
  Нужны полный переходный ZIP и SHA-256. Старый неполный релиз не применяется.
* Архив и все его файлы проверяются до установки, пути ограничены. Код старой
  установки сверяется с известным профилем или сохранённым исходным комплектом.
* Создаётся отдельная папка рядом с исходной. В неё попадают согласованный снимок
  SQLite, сессии, настройки, продукты и тексты. Проверяются конфликты, отдельное
  окружение, зависимости и main.py --self-check. Публичные ключи центра применяются
  автоматически, личные ключи и MANAGER_ID сохраняются.
* Только затем атомарно меняется data/active-installation.json в исходной папке.
  Привычный запуск всегда читает эту запись и запускает актуальную базу.
* Если подготовка не удалась, запись не меняется и запускается прежняя версия.
  Неверная/недоступная запись активной установки останавливает запуск: возвращаться
  к устаревшей базе молча нельзя. После запуска новой версии автоматического отката
  нет — она могла уже отправить сообщение.
* Блокировка запуска действует весь срок работы дочернего отправителя. Обновления
  происходят перед запуском; работающая рассылка для установки не прерывается.

## Переход через старый автообновлятор

build_platform_release.py дополнительно собирает telegram_ai_sender_vVERSION.zip
и SHA-256. Этот архив содержит ровно список файлов, который принимает старая
2.0.19. В launcher.py и main.py встроен весь проверяемый переходный комплект:
дополнительные команды и отдельный установщик менеджеру не нужны.

Старый автообновлятор сначала сам сохраняет резервную копию. Загрузчик восстанавливает
из неё прежнее ядро и личный каталог/промпты в отдельную папку, а актуальные данные
берёт из действующей базы (не из старого резервного снимка). После этого выполняет
обычный проверенный переход. При сбое остаётся доступной сохранённая старая версия.
Неизвестное ядро или неполная резервная копия требуют проверки владельца.

Это работает для установок, уже запускающих launcher.py и получающих обновления.
Если прежний ярлык запускает main.py напрямую и автообновлений в нём нет, удалённо
добавить обновление без единого первоначального изменения запуска невозможно.
Такие установки нужно выявить перед выпуском. В исходной рабочей папке владельца
start.bat отсутствует; её переход пока не выполнялся.

## Публикация и проверка

Сборка сама ничего не публикует. Рабочая ветка публикует только отдельный prerelease
с latest=false; существующие пользователи его автоматически не получают. При будущем
стабильном выпуске нужны одновременно bridge ZIP/его SHA-256 и переходный ZIP/его
SHA-256 в одном релизе с совпадающим номером версии. Старый workflow стабильного
релиза не заменён автоматически этим изменением.

Локальные тесты проверяют сбои, сохранение данных, атомарное переключение, повторный
запуск, блокировку дубля, отказ от старой базы при повреждённом указателе и совместимость
архива со старым автообновлятором. tests/bridge_smoke.py использует настоящее ядро
2.0.19 и проверяет старый apply_update → встроенный загрузчик → установка зависимостей
→ новый --self-check на вымышленных данных. Telegram и AI в этом тесте не вызываются.

Сетевая работоспособность конкретного менеджера и первая контролируемая отправка
проверяются отдельно. Общий выпуск остаётся закрыт до согласованных живых переходов.
Папки предыдущих версий автоматически не удаляются; место для копии базы и окружения
нужно сохранить. Нельзя запускать старую базу вручную после работы в новой.
