# Подключение бизнеса к общему ядру

## Что выделено

`product_catalog.py` загружает и проверяет бизнес-пакет без Telegram, базы и
сетевых вызовов. `ai.py` выполняет общий процесс: определить продукт, проверить
поля, заполнить промпт, вызвать выбранные адаптеры, выполнить ИИ-запрос и
проверить результат. `context_adapters.py` содержит явный реестр интеграций и
контракт `ContextAdapter(enrich, required_fields)`. Ядро не выбирает интеграцию
по названию бизнеса. Из пакета нельзя импортировать произвольный Python-код.

Существующие продукты и промпты остаются в products.json и prompts/.
Для Право_ООО/Право_ИП включён `arbitration`; остальные продукты этот API не
вызывают. Старый плоский реестр поддерживается; новые пакеты могут использовать
обёртку `{"schema_version": 1, "products": {...}}`.

## Пример независимого бизнеса

См. examples/service_business. Чтобы выбрать его, в .env задайте:

```
BUSINESS_PRODUCTS_FILE=examples/service_business/products.json
```

Относительный путь считается от корня приложения. Каталог prompts/ должен
лежать рядом с выбранным реестром. Без настройки используется штатный реестр.
Это выбор пакета установки, не механизм прав доступа к продуктам.

Excel для примера: **Юзернейм, Продукт, Компания, Сайт**. В колонке Продукт
указать «Услуги для бизнеса» или «сервис». ИНН и ФИО этому пакету не нужны.
Текущие продукты ДВК по умолчанию сохраняют обязательные ИНН и ФИО.
Общие обязательные колонки транспорта: Юзернейм и Продукт.

Настройки продукта:

- `prompt`: относительный путь внутри prompts/; выход через ../ и symlink запрещён.
- `aliases`: дополнительные названия продукта из Excel, без конфликтов с другими.
- `version`: строковая версия бизнес-настроек; по умолчанию «1».
- `columns`: соответствие внутренних ключей полей названиям колонок Excel.
  По умолчанию inn → ИНН, full_name → ФИО. username/product зарезервированы ядром.
- `required_fields`: обязательные ключи из columns. По умолчанию inn, full_name.
- `model`: модель ИИ; по умолчанию gpt-5-mini.
- `tools`: список разрешённых инструментов ИИ: пока web_search или пустой список.
- `context_adapters`: ID интеграций из реестра; по умолчанию пустой список.

В промптах доступны `{{company}}`, `{{website}}` и другие объявленные поля.
Старые заполнители ИНН сохранены: «Конкретный ИНН», `{ИНН}`, `{{ИНН}}`.
Если ИНН задан и заполнителя нет, он добавляется в начале, как раньше.
Другие поля включайте в промпт явно. Неизвестный или пустой заполнитель блокирует
генерацию. Обычный JSON и одиночные фигурные скобки не интерпретируются.

Формат ответа пока общий: маркеры ГОТОВОЕ СООБЩЕНИЕ / КОНЕЦ СООБЩЕНИЯ и
ТРЕБУЕТСЯ РУЧНАЯ ПРОВЕРКА. Он одинаков для всех пакетов и сохранён совместимым
с восстановлением очереди. Подготовленные сообщения сами не пересоздаются
после редактирования пакета: сохранённый текст остаётся текстом очереди.

Пакет проверяется перед импортом/исследованием: схема, поля, пути, промпты,
алиасы, инструменты, адаптеры. Ошибки пакета не должны тратить ИИ-запросы.
При импорте реестр загружается один раз для всего файла. Анализ повторно читает
актуальный пакет перед запросом. Редактировать пакет во время работы очереди
не рекомендуется; полноценная атомарная активация версий ещё не реализована.

## Новая интеграция

Для нового источника разработчик добавляет адаптер через общий контракт и
регистрирует ID. Продукт выбирает его конфигурацией. Требуемые адаптером поля
должны входить в обязательные поля продукта. Новые неизвестные API не появляются
из одного промпта. Ключи остаются в локальных настройках, не в пакетах.

## Границы текущего этапа

Это выделение продуктового слоя, не завершение всей платформы. Хранение пока
использует совместимые поля SQLite (включая необязательные inn/full_name);
дополнительные поля используются при рендеринге промпта. Полная исходная строка
и версия пакета ещё не сохраняются как отдельный универсальный объект клиента —
это нужно учесть при следующем этапе базы и синхронизации.

Компании/подписки, синхронизация исключительно владельцу, объединение выпусков
Windows/macOS, установка бизнес-пакетов через интерфейс и совместимый переход
с 2.0.19 остаются следующими этапами. Старый упаковщик не включает новые модули;
этот код нельзя публиковать существующим workflow как готовое автообновление.
Ни старый allowlist, ни номер опубликованной версии этим этапом не меняются.

Проверки: `python -m unittest discover -s tests -v`. Они используют подставные
ответы ИИ/API, не отправляют Telegram-сообщений и не доказывают работу обеих ОС.
