# Обновления и общий запуск: текущий этап

## Рабочая установка владельца

Фактически используется Windows, папка telegram_ai_sender_V2.0, запуск
`python main.py`, version.txt = 2.0.9, Git HEAD 1b4e2fc, feature/auto-updates.
Локальные изменения: products.json (Николай), prompts/bg.md, prompts/credit.md;
неотслеживаемые Nikolai.md и khimikaty_dlya_rasteniy.md. Последний — приостановленный
черновик, не добавлять в действующий реестр. Полный резерв сделан пользователем.
Это отличается от предположительно установленных у менеджеров 2.0.19.

Владелец продолжает запускать `python main.py`. Обновление вручную, только
проверенными версиями. Безопасный переход не должен требовать git pull/reset
или перезаписывать рабочую папку. Ниже — инструмент подготовки, не команда
массового обновления и не готовый опубликованный релиз.

## Общий запуск менеджеров

Windows: `start.bat`; macOS: `bash start_mac.sh`. Обе оболочки вызывают start.py,
который использует платформенный путь venv, проверяет Python >= 3.11 и устанавливает
зависимости при изменении SHA-256 requirements.txt. Метка установки записывается
только после успешных pip install и pip check. Незавершённый существующий venv
не удаляется. TLS/проверки пакетов не отключаются, pip автоматически не обновляется.
Код завершения приложения возвращается оболочке.

`python start.py --check` проверяет структуру без установки, запуска, сетевых
запросов и чтения секретов. Это не проверка работоспособности приложения.
`python start.py --no-updates` запускает main.py в подготовленном venv без launcher.
Прямой запуск владельца main.py сохранён и использует его выбранный Python.

Эти новые оболочки не следует копировать поверх старой установки отдельно от
остальных файлов. В новом приложении требуется настройка центрального доступа.

## Подготовка кандидата вручную

manual_update.py использует только стандартную библиотеку Python, не подключается
к Telegram, не скачивает ничего, не изменяет source и не активирует обновление.

1. Разработчик собирает новый формат:

   ```text
   python manual_update.py build --source PATH_TO_REVIEWED_CODE --output NEW_PACKAGE.zip
   ```

   Только явный список модулей/инструкций и prompts/*.md. .env, session, data,
   authority signing.key и Git не входят в пакет. Архив не перезаписывается.
   Рядом создаётся .sha256; контрольную сумму получать из доверенного источника.
   Локальная сборка с текущим version.txt не является опубликованным релизом.

2. Дождаться завершения рассылки и остановить ВСЕ процессы исходной установки.
   У старых версий нет общего блокирующего файла; инструмент не может доказать
   отсутствие старого процесса. --sender-stopped — явное подтверждение этого
   обязательного условия, не автоматическая проверка.

3. Подготовить **новую соседнюю папку**, например через cmd:

   ```text
   python manual_update.py prepare --source "C:\PATH\working" --package "C:\PATH\NEW_PACKAGE.zip" --sha256 TRUSTED_64_CHARACTER_HASH --destination "C:\PATH\candidate" --sender-stopped
   ```

   Это пример с заполнителями, не готовая команда пользователю. Нужны фактические
   пути к проверенному пакету. Папка destination должна отсутствовать и находиться
   вне source. До любых действий проверяются SHA-256, состав, пути, версии,
   пофайловые хэши и синтаксис Python. Ограничены размер и число файлов; запрещены
   дубли, коллизии регистра, symlink и опасные Windows-имена. Одинаковая/более старая
   версия не устанавливается этим путём.

4. Прочитать update_report.json в candidate. В нём только пути/статусы, без
   содержимого .env и клиентских данных. Exit code 2 означает конфликты.
   Существующая исходная установка остаётся нетронутой при успехе и отказе.

Правила сохранения:

- Для известных файлов Git читается HEAD:filename, без fetch/reset/checkout.
  Локально изменённый код сохраняется в кандидате; пересечение с изменениями
  нового пакета отмечается конфликтом. Для папок без Git надёжного исходного
  состояния нет: рабочая папка остаётся резервом, кандидат требует ручного ревью.
- products.json объединяется по полям, с учётом базового Git-файла при наличии.
  Новые настройки из пакета добавляются; локальные изменения/удаления сохраняются.
  При конкурирующих изменениях сохраняется локальный выбор и отмечается конфликт.
  Поддержан переход плоского реестра к schema_version=1 без потери локальных продуктов.
- Изменённые/неизвестные локальные промпты сохраняются; конфликтующие версии
  остаются также в исходном доверенном ZIP для ручного сравнения. Все дополнительные
  локальные .md-промпты, включая приостановленные черновики, копируются.
- .env, корневые *.session и рабочие data копируются только в локальный кандидат.
  SQLite/.session снимаются через SQLite backup и integrity_check, с учётом WAL.
  Служебные WAL/SHM не копируются отдельно. Старые updates/backups и центральные
  access_authority (включая signing.key) в менеджерскую копию не входят.
- venv, .git, .env.authority и произвольные файлы вне этого списка не копируются.
  Дополнительные пользовательские ресурсы нужно выявить до переключения.

## Чего подготовка НЕ делает

ready_to_run=false и dependencies_installed=false записываются намеренно.
Не происходит установки зависимостей, запуска/подтверждения нового приложения,
автоматического разрешения конфликтов или переключения рабочей установки.
Нельзя считать подготовленную папку готовой только потому, что команда завершилась.

Перед переходом: разрешить конфликты, проверить реестр/промпты и настройки центра,
установить зависимости в отдельный venv, выполнить тесты и проверку без рассылки.
Нельзя одновременно запускать source и candidate с одной Telegram-сессией.
Пока кандидат не начал реальную работу, возврат к исходной папке сохраняет
исходное состояние. **После новых отправок/записей в кандидате простой возврат
к старой базе опасен повторами:** сначала нужно перенести/сверить актуальные данные.

## Оставшиеся условия выпуска

- Живые проверки Windows/macOS ещё не выполнены. Проверка bash-синтаксиса в Linux
  не заменяет проверку Mac; тесты Python не заменяют выполнение start.bat в cmd.
- Автообновлятор 2.0.19 и старый release workflow не понимают новый полный формат.
  Они оставлены неизменными; требуется отдельный совместимый путь автоматического
  перехода и тесты отката/миграций до выпуска менеджерам.
- Подписки компаний, надёжная синхронизация исключительно владельцу и развёрнутый
  центр ещё нужны. Админский бот выбран пользователем: @asdvk2026_bot; токен не в Git.
- Новая подписка должна ограничивать срок офлайн-разрешения, чего текущий черновик
  доступа ещё не реализует.

Проверки инфраструктуры: `python -m unittest discover -s tests -v`.
Тесты подготовки не отправляют сообщения, не используют настоящие секреты и не
запускают автоматическое обновление действующих пользователей.
